- **踩坑：.bat 的编码/换行**。矩阵实测（UTF-8/GBK × CRLF/LF × chcp 有无）结论：
  ① **不能在 .bat 里 `chcp 65001`** —— cmd.exe 改代码页后在**错误字节偏移**继续执行，文件头 REM 注释被当命令跑（一堆"不是内部或外部命令"）；② **必须 CRLF**，LF-only 同样错位；③ 正文**纯 ASCII**（提示改英文）。最终版：ASCII + CRLF + 无 chcp + 无 BOM。
  首版用 UTF-8+中文+chcp，实跑确实炸了（构建步骤本身正常，只有注释行报错）→ 已重写为 ASCII 版。

## 服务器地形"未发现真实瓦片⇒回落合成"诊断
- 现象：前端 HexGenPanel 报"生成服务未发现本地真实地形瓦片（/www/wwwroot/wargame/hexgrid）⇒ 高程退回合成"。该文案由 `HexGenPanel.tsx:65` 直接用 `dem.terrain_dir`（来自 GisApi `/api/capabilities` 的 `dem.terrain_dir`）拼出。
- 根因：GisApi 解析出的 `terrain_dir = /www/wwwroot/wargame/hexgrid`，这是**六角格输出目录**（不是地形输入目录）。`ResolveDir` 空配置时永远落 `<repo>/data/terrain`，不可能拼出 `hexgrid` ⇒ 服务器 appsettings 把 `TerrainDir/TerrainDirLinux` 显式写成了 `hexgrid`（输入/输出指反了）。该目录被 `Directory.CreateDirectory` 建出来但无 `terrain_manifest.json`/`*.ter` ⇒ `TerrainSampler.Available=false` ⇒ auto 回落合成。
- 修复（服务器侧）：把 GisApi 的 `TerrainDirLinux` 指向**含 terrain_manifest.json 与 *.ter 的目录**（发布包内为 `server/data/terrain`，绝对路径最稳），或把 `HF_REPO_ROOT` 设为含 `server/data` 的目录让默认 `data/terrain` 生效；改完重启 GisApi，`curl 127.0.0.1:5180/api/capabilities` 看 `dem.real_tiles_available` 应为 true。
- 代码改进（本地已改，待重新打包）：① `GisApiService` 构造注入 `ILogger`，启动即打印 `terrain_dir`/数据路径及命中情况（目录不存在 / 有目录无瓦片 / 已加载），把静默回落变可查；② 前端 `HexGenPanel.tsx:65` 提示补一句"把 TerrainDir 指向含 terrain_manifest.json 的目录"。两处均已编译/构建验证（GisApi 0 警告 0 错误）。
